# Native recordings playback — investigation and design (#148)

Issue: [#148](https://github.com/tommaso-vaccari/BeepBar/issues/148). Integrated into `dev` with PR #152; the follow-ups (watch progress, menu Play, refresh at every sync, Now Playing, zoom, compact controls) are PR #154 (draft, `feature/recordings-progress-and-player`), described in the last sections of this file.

Goal: Play on a recording streams it in a native BeepBar window instead of opening Webex in the browser. Webex sign-in happens automatically in the hidden Recman web view (the Polimi single sign-on is already there), using the user's confirmed Polimi email. Anything that fails falls back to the browser, as before. The feature exists in memory only while used.

All findings below come from `scripts/recman-probe.sh play` / `lab` runs on 2026-10-11 with the account owner's authorization. Outputs are reduced to hosts, paths with ids masked, field names, key names and types: no tokens, cookie values, ids, titles or emails. Webex's web-player API is internal and can change without notice: every step must fail safe to the browser.

## How Webex gets from the player link to the stream

1. The Recman preview gives `https://politecnicomilano.webex.com/<…>/ldr.php?RCID=<id>`.
2. `ldr.php` answers **`302`** with `Location: …/sites/politecnicomilano/recording/playback/<uuid>` (32 hex) **when the request's `Accept` includes `*/*`** — no cookies needed, any User-Agent. With a `text/html`-only `Accept` it answers `200` with a 15 KB page that does not contain the uuid (this misled the first probe). So **no web view is needed for the uuid**: a no-follow GET with `Accept: */*`. A `200` means "unknown layout" → browser fallback. (If a web view were ever needed, cancelling the main-frame navigation to `/recording/playback/<uuid>` yields it in ~0.8 s.)
3. Stream API: `GET https://politecnicomilano.webex.com/webappng/api/v1/recordings/<uuid>/stream?siteurl=politecnicomilano`.
   - Signed out: `403` with a JSON body (`requireLogin`, `canPlayback`, `preventPlayback`, `passwordProtected`, `needPassword`, `preventDownload`, …).
   - Signed in: `200`, with `downloadRecordingInfo.downloadInfo.{hlsURL, mp4URL, dashURL, audioURL, playerCoverURL}`, `mp4StreamOption`, `duration`, `recordName`, `chapterLayout`, `transcriptStatus`, `mediaDetectInfo`, `playerPanels`, `showAISummary`, … (shapes only).
   - Works from a plain `URLSession` with cookies only (no CSRF header, no Referer, no page context). The **only cookie required is `ticket` on `.webex.com`** (session cookie): without it `403`, with it alone `200` (confirmed again ~25 min after sign-in).
   - `requireLogin` is **not** a signed-out flag (it reads 1 on the 200 and 0 on the 403): decide on the HTTP status and on the presence of `hlsURL`.
4. `hlsURL` (`https://nfg1wss.webex.com/nbr/…/hls.m3u8?trackingID=…`) is a single-level HLS playlist of byte-range segments of one 1080p mp4. **AVPlayer plays it without any cookie** (ready in ~5 s; 136-min test lecture). The same URL still played 10 minutes later; longer lifetimes are not measured.

## Webex sign-in

- Signed-out chain: playback page → `webappng/sites/politecnicomilano/login?siteurl,viewFrom,login_return_url` → `idbroker-eu.webex.com/idb/…` → `doSSO.jsp` **email page** (`input#IDToken1[type=email]`, `button#IDButton2[name=btnOK]`) → `idbroker-eu…/globalLogin` → `shibidp.polimi.it` → `aunicalogin.polimi.it`, which **completes on its own with the Polimi SSO cookies** already in the Recman store → back to the playback page.
- The email page comes back whenever Webex's session cookies are missing, even with persistent cookies such as `CK_LastLogin` (1 year); it is never prefilled.
- **Passing the email in the webappng login URL (`…/login?…&email=<address>`) skips the email page** and goes straight to Polimi's IdP (tested with a placeholder address, stopped before the IdP). So no form filling by script is needed.
- With Polimi cookies plus idbroker's session cookies (`cisPRODEUiPlanetDirectoryPro`, `amlbcookie`, `amlbcookiesm`, idbroker `JSESSIONID`) the sign-in is **silent** (no email page): login → idbroker → server redirect → webappng → playback, stream API `200` after ~7 s, and the new `ticket` works from `URLSession`.
- The `email` hint routes by domain: with a `mail.polimi.it` placeholder idbroker posts straight to Polimi's IdP; with `example.com` it shows its own password page; `login_hint` alone is ignored. A full sign-in with a **placeholder** address stalled on a blank `idbroker-eu…/idb/Consumer/metaAlias/<id>/sp` after the Polimi SSO completed (probably because the asserted identity differs from the hint). **Whether the hint with the user's real email completes unattended is unverified** and must be confirmed live with the owner's consent; keep the visible-window fallback.
- Every Webex cookie that matters is a session cookie (`ticket`, `accessToken`, `userHubToken`, the idbroker ones); persistent ones are only `CK_LastLogin`, `wxidIstio`, `CisTrackingID`, `WBX_ttm…`. The v2 session file keeps session cookies, so after a relaunch: `ticket` alive → no sign-in at all; only idbroker alive → silent ~7 s sign-in; nothing alive → hinted sign-in.
- After sign-in Webex sets ~15 cookies (`.webex.com`, `idbroker-eu.webex.com`, `nfg1wss.webex.com`, `politecnicomilano.webex.com`), mostly session cookies; a few short-lived trackers.

## Chosen design

1. `URLSession`, no cookies, no redirects followed, `Accept: */*`: GET `ldr.php` → `302` → uuid from `Location`. Never load the player page (it pulls u2c catalogs, device registration, KMS, telemetry and Amplitude, and would play audio hidden).
2. `URLSession` to the stream API with the Webex cookies of the Recman store (only `ticket` matters) → `hlsURL` → native player (cookie-less).
3. On `403`: sign in to Webex in the hidden Recman web view through the webappng login URL with `email=<confirmed Polimi email>`; Polimi SSO completes; wait for `ticket`; retry step 2 once. If a page asks for the user, the existing sign-in window flow applies. A `200` without `hlsURL` (no HLS for this recording) → browser, without signing in: live, signed out was only ever a `403`.
   - After the sign-in, whatever its outcome, the hidden web view is reset to `about:blank`, so no Webex page keeps running. Whether the final webappng → playback hop is a main-frame navigation (which the navigation policy can cancel) must be confirmed live; if it were in-page (SPA) routing, the `about:blank` reset still bounds its cost to the moments before the ticket is seen.
4. Any unexpected page, status or shape → open the player link in the browser as today.

Decisions by the product owner: native window (not QuickTime Player); email read from the WeBeep profile (since 2026-10-11 used without a confirmation step, see below); player MVP = system controls (PiP, AirPlay, Now Playing), speed 0.5–3x, ±10/30 s skips and shortcuts, resume where you left off (saved on pause/close only, tied to the watchlist/seen state), recovery after errors or expired URLs. v2: transcript (VTT) with search, chapters, audio-only (`audioURL`), bookmarks, slide capture, next-lecture queue, floating window. Out: adaptive bitrate (single level), offline download (#87, honour `preventDownload`).

Product decision (2026-10-11): when Webex needs a sign-in and no Polimi email is available (typed, saved, or from the WeBeep profile) (`RecmanBrowserError.needsEmail`), Play shows the error «Non è stato possibile aprire questa registrazione.» / "Couldn't open this recording." — no Webex email page is shown to the user.

Product decision (2026-10-11): no name/surname field. BeepBar does not store the user's name, username or email today (only the numeric Moodle user id); deriving the email from a name is unreliable (homonyms get numbered addresses, accents, apostrophes, double surnames) and would add personal data. Instead the Recordings settings section gets one **email field**, prefilled from the WeBeep profile (`fetchOwnEmail`, only when `availableFunctions` lists it), confirmed or corrected by the user (validated by `PolimiEmail`), with an explanation that it is used only to sign in to Webex automatically for in-app playback. It is stored only in `recordings-session.plist` and deleted with it (turn off, logout, site or account change). If the profile read fails the field stays empty for the user to fill in.

Product decision (2026-10-11, later the same day, `fix/rnp-email-confirmed-by-default`): **the profile's address is used without a confirmation step.** Reason: Play without a hand-confirmed address kept ending on "Couldn't open this recording." for the owner. How it works (`RecordingsController.learnEmail`):
- When no address is known (none typed, none in the session file), the first Play, or the Settings field, reads the WeBeep profile once per epoch, shared between callers (a Play during the Settings read waits for that same answer), never at rest and with no timer. A valid `PolimiEmail` becomes `confirmedEmail` with `emailFromProfile` set, is written into the session file at once (`vault.updateEmail`) and by every later save (fingerprint included), exactly like a typed address. The field shows it as in use and "taken from your WeBeep profile".
- The student wins: an edit or removal in this launch stops any later profile answer (`emailEditedByUser`); a removal is also remembered for the account across launches in `recordings-email-declined.v1` (the numeric WeBeep user id only, no address), since an empty session file can't tell "removed" from "never set". Entering an address again, turn-off, logout and account change remove that marker.
- An answer arriving after a turn-off, logout or account change (new `emailEpoch`) is dropped; `WeBeepAuthenticationController.profileEmail` also checks the account didn't change. Profile unavailable, failed or not a Polimi address: nothing changes, Play still ends on `needsEmail`.
- Diagnostics: `play: start email=confirmed|profile|none` (`confirmed` = typed or read from the file), never the address.
- Compliance: there is no longer a user action authorizing the address before Webex receives it (C05 in the compliance wiki).

Requirements recorded for F by reviews: carry the email through the controller's save path and its fingerprint; verify a relaunch reaches the stream without a new Webex sign-in (the 12 h floor must not drop the cookie that matters — `ticket` is a session cookie, so it is kept); any `fetchOwnEmail` failure means "ask the user", never a sync error; specs IT/EN and compliance wiki must say the session file also holds Webex cookies and the Polimi email; measure `otool -L` (no AVKit), dyld images and launch, 30-min idle wakeups, memory after 1 and 10 play/close cycles, `scripts/quit-probe.sh` with the player open.

Player ownership and lifecycle for F (from C's review): the long-lived `RecordingsController` owns the player; call `close()` on logout, Recordings disable and account change (the stream belongs to the old identity), but **not** from `windowClosed()` (a lecture keeps playing with the settings window closed). The player has no deinit teardown. While BeepBar is `.regular`, ⌘Q from the main menu and Dock Quit become new quit entry points: rerun `scripts/quit-probe.sh` and try both by hand with the player open during a sync. `WeBeepAuthenticationController.chooseRoot` restores `.accessory` unconditionally after its modal panel and can drop the Dock icon if a Play started meanwhile: make it restore only if still `.regular`.

## Player findings (package G, macOS 27, verified in tests or a spike)

- `AVPlayerItem.audioTimePitchAlgorithm` defaults to `timeDomain` (apps built for macOS 12+); the player sets it anyway, so a future default cannot switch lectures to the costlier `spectral`.
- `AVPlayerView` (macOS 13+) has `speeds` (system default 0.5, 1, 1.25, 1.5, 2), `selectedSpeed` and `selectSpeed:`; `selectSpeed:` sets the player's `defaultRate`, and `defaultRate` is KVO-observable, so the view's own speed menu is followed. The `AVPlaybackSpeed` objects are built at runtime (no AVKit link). Whether the floating controls actually show a speed menu could not be checked without showing a window: the title-bar menu is the guaranteed path.
- Controls style (owner feedback, 2026-10-14: the floating panel sat too high and was too big): the view uses the inline style (`AVKitLoader.controlsConfiguration`, raw values from `AVPlayerView.h`: None 0, Inline 1, Floating 2, Minimal 3, Default = Inline), with frame stepping, sharing, full-screen and timecode buttons off. Measured in a 960x540 view: floating = a 457x100 pt panel whose bottom is 86 pt above the edge; inline = a 750x36 pt bar 6 pt above the edge (±15 s, play/pause, elapsed, scrubber, remaining, speed) plus two small top-corner pills (AirPlay, volume). AVKit always uses the floating style in full screen (header, macOS 11+). The inline controls sit in the same sibling branch as the floating ones, so `PlayerVideoViews` still tells video from controls. Picture in picture is not offered: `allowsPictureInPicturePlayback` defaults to NO and the player never set it, with either style.
- `AVPlayerView`'s own keys: Space toggles playback, ←/→ pause and step one frame, J/K/L shuttle (J plays backwards); Shift+arrows, F, M, digits and `<`/`>` do nothing. The window takes all the player's shortcut keys first (`RecordingPlayerWindow`), replacing frame stepping and reverse play, which are useless for a lecture and costly on a stream; ⌘/⌃/⌥ chords pass through.
- AVFoundation guarantees only 1.0–2.0 for every ready item: above 2.0 needs `canPlayFastForward`, below 1.0 `canPlaySlowForward` (AVPlayerItem.h). The local MP4 fixture has both; whether Webex's single-level HLS does is **unverified** and must be checked live (if not, those speeds simply stay disabled).
- For F: `onPositionCheckpoint` also fires synchronously at the start of a `play` that replaces the lecture on screen, with the old lecture's `recordingID`, so every report says which recording it is about. During a resume, play/pause requests only set whether playback starts once the resume seek lands. Quitting reports nothing (not on the quit path): the last pause is what survives.

## Package F as built (`feature/rnp-app-integration`)

- `RecordingsController` owns one `RecordingPlaying`, created by the first Play that has a stream. Play is a queue job like the others (the Recman browser runs one operation at a time): `browser.stream(for:email:)` → `player.play(…, startAt:, recordingID: recording.id, cookies: [])`. `playbackUnavailable` and any unknown error (including non-`RecmanBrowserError`) fall back to the browser through the player link; `needsSignIn`, `unavailable`, `needsEmail` and cancellation are reported like any request failure (`needsEmail` shows the product-decision sentence). A native Play always asks for a fresh stream; only Copy link and the browser fallback use the cached player link. When the lookup fails after the archive gave the player link, `stream(for:)` throws `RecmanStreamFailure` carrying it, so the browser fallback (Play and recovery) opens that link without walking Recman a second time (PR #152 review); decisions and logs read the wrapped cause, and cancellation is never wrapped. In a recovery this means an unreachable Webex after the link was found opens the browser with that link, where a Play reports `unavailable`. The in-memory address records its WeBeep account (`emailAccount`) and is dropped when the account changes, also before any Polimi session exists; `confirmEmail` refuses an address while no account is known.
- Email: `RecmanSessionVault.save` takes `email:` with no default (a caller that forgets it cannot erase the address), the vault's "unchanged" record includes it, and `updateEmail` rewrites only the address in an existing file (Settings edits with no browser open). With no session file yet the address lives in memory and the next sign-in's save writes it; quitting before that loses it (the field is then prefilled again but unconfirmed). `fetchOwnEmail` is reached through an injected closure in `WeBeepAuthenticationController` (`availableFunctions` check, non-interactive token read, same-account check after the answer); every failure is nil.
- Positions: `RecordingResumePoints` (Core), one value in `UserDefaults` (`recordings-resume.v1`) holding owner, and id → seconds (max 200, oldest out first); written only from `onPositionCheckpoint`, only when it changes; keyed by `RecordingsStudyState.identity` (year:course:id). "Finished" = within max(30 s, 2 % of the duration) of the end: forgotten, acknowledged as seen (Play already acknowledged it), starts over. Re-pressing Play on the lecture already on screen resumes from the last saved place, not the instant (the replacement report arrives inside `play`, after `startAt` was chosen).
- Recovery: `.duringPlayback` → one fresh stream at the reported position (per Play), else browser; `.beforeReady` → browser. The recovery runs as a queue job (`stream(for:)` may show the sign-in window; here the student is watching, so that is accepted) and closes the Recman browser afterwards when no page is on screen. A second mid-lecture failure after a recovery goes to the browser even if the first recovery worked (an address that lives less than the lecture would otherwise loop).
- Lifecycle: `closePlayerForIdentityChange` (turn-off, logout and university change via `turnOff`, account change, a saved session of another account) clears the accepted-reports table first, so the close's own checkpoint is refused. `windowClosed()` leaves the player alone. `chooseRoot` decides with the pure `panelPolicyOutcome` and, with a lecture open, hands the policy to restore to the player (`adoptPolicyToRestore`) instead of dropping the Dock icon.
- G's P2s: `pause()`/K/Space during an unsettled resume now pause a player the student started from the system controls; `canPlayFastForward`/`canPlaySlowForward` are read inside the main-actor hop (`rateSupportObserved`).
- Manual checks instead of tests: that the email is never logged (no log call in `RecordingsController`, `WeBeepAuthenticationController.profileEmail` or the settings view mentions it, except `play: start email=confirmed|profile|none`, which logs only where the address came from; grep before every release) and that the quit path is untouched (`prepareForTermination` and `prepareForMenuQuit` do not reference the player; `scripts/quit-probe.sh` with a lecture open). Before the release, also check by hand how `chooseRoot` acts on `panelPolicyOutcome`: the decision is tested, but not that each outcome does what it says (`.handToPlayer` hands the policy to the player, `.restore` puts it back, `.leave` changes nothing; mutation 11c survived). On a Mac:
  1. Start a lecture, then choose another folder in Settings, which opens the folder panel. Confirm and cancel. BeepBar keeps its Dock icon and its Cmd-Tab entry while the lecture is open, and loses both once the lecture closes.
  2. With no lecture open, choose a folder. The Dock icon goes away when the panel closes.
- A session file that could not be read at launch keeps its email through the next save (`keepingFileEmail`); the profile is asked once per session (not at every Settings appearance), also after a failure.
- Not done in F: measurements (`otool -L`, dyld images, launch, 30-minute idle wakeups, memory after 1 and 10 cycles, `scripts/quit-probe.sh` with the player open, ⌘Q and Dock Quit by hand); the live checks listed below.

## Play opened the browser on the first Mac run (`fix/rnp-play-falls-back-to-browser`)

Report: on a Mac, signed in with a real account, Play opened the Webex player in the browser instead of BeepBar's window. The fix was written without a Mac (static analysis only, Core tests run on Linux); the live cause is confirmed by the logs below.

Every way a Play reaches the browser was traced. Not the cause: the wiring (row button, double click and Return all call `play`, which always asks for a stream; no flag, no gate besides `access == .ready`, no cached link for Play); `needsEmail` (it shows the message and opens nothing, so a Play without a confirmed email never reaches the browser); a non-Polimi error from the resolver (network errors become `unavailable`, which is reported, not the browser). What remains is `playbackUnavailable` (silent fallback by design) or a player failure before the stream was ready, and until this fix both logged one identical line. Ranked hypotheses:

1. **`passwordProtected` on the signed-in 200** (fixed). `WebexStreamAPI.decode` refused any answer with `passwordProtected` true, even with an `hlsURL`. The flag describes the recording, like `requireLogin` (1 on the signed-in 200), while `needPassword` is the viewer's state; Webex plays a protected recording to a signed-in member of the site without asking anything, which is exactly "it opens in the browser and plays there". The probes recorded the field names only, not their values, so this is the likeliest silent refusal, not a measured one. Now only `needPassword` (or `preventPlayback`/`canPlayback` false) refuses; a protected recording without an `hlsURL` still says `password-required`. Fail-safe: a stream AVPlayer can't open still ends in the browser.
2. **The hidden sign-in** (first Play, no `ticket` yet): back at the playback page without a ticket within 5 s (the ticket might be set only by the playback page, whose load is always cancelled), or a main-frame hop to a host off the measured chain (refused while hidden). The login URL also leaves `viewFrom` out (not recorded live). Logged as `step=sign-in ended result=back-at-playback-without-ticket` or `result=refused-host host=…`, with the trail of hosts.
3. **`ldr.php` not answering with a recognized playback page** (a 200, or a `Location` in another form such as `…/recording/<uuid>/playback`): logged with the status and the path's shape, ids masked. The parser was not relaxed without evidence.
4. **The player failing before ready** (AVKit not loaded, the HLS refused): now logged with AVFoundation's domain and code and the underlying error.

Also fixed: the rows' menu item «Apri nel browser» / "Open in browser" called Play (BeepBar's player) and the Play button's tooltip still said "Open in browser"; the item now opens the browser on purpose (`RecordingsController.openInBrowser`), the button says «Riproduci» / "Play", and the Recordings introduction no longer says lectures play in the browser. `RecordingResumePointsTests.applyingReports` did not compile (`#expect(points.apply(…))` on a mutating method); its calls now run outside `#expect`.

### Diagnostics

Notice-level lines, category `playback` (the player's own lines are in `player`), written only while a Play runs. They hold step names, HTTP statuses, decisions, flags as 1/0/-, Webex and Polimi host names and masked path shapes: never an address, a uuid, a cookie, a title or the email. On the Mac, before pressing Play:

```
log stream --style compact --predicate 'subsystem == "io.github.tvaccari.beepbar" AND category IN {"playback", "player"}'
```

or afterwards `log show --last 15m --style compact --predicate '…same…'`. A Play logs, in order: `play: start email=confirmed|profile|none`; `stream: step=archive-player-link found form=loader`; `stream: step=player-link form=loader status=302 location=playback-page`; `stream: step=api attempt=first ticket=absent status=403 result=signed-out …`; `stream: step=sign-in start`, `stream: step=sign-in ended result=… window=hidden|shown trail=…`, `stream: step=sign-in done`; `stream: step=api attempt=after-sign-in … result=stream|unavailable(<reason>) json=object hls=present needPassword=0 passwordProtected=1 …`; then `play: stream found, handing it to the player` or `play: fallback=browser|none reason=native-unavailable|no-email|needs-sign-in|unreachable|cancelled|stream-error error=…`, and for a stream the player couldn't play `play: player failed phase=before-ready recovery=browser reason=player-failure error=<domain>(<code>) underlying=…`.

## Now Playing: lecture, course and course picture (PR #154)

Problem: Control Center's Now Playing (and the media keys HUD) said only "BeepBar". Cause, measured with a probe reading MediaRemote's now-playing record (macOS 27): `AVPlayerView` publishes Now Playing itself (`updatesNowPlayingInfoCenter`, default on) and on macOS takes title, artist and artwork only from the stream's own metadata; a Webex HLS stream has none, so the system shows the app name. The iOS hooks (`AVPlayerItem.externalMetadata`, `AVPlayerItem.nowPlayingInfo`, `MPNowPlayingSession`) do not exist on macOS (selectors absent at runtime even with AVKit loaded), and writing `MPNowPlayingInfoCenter` next to AVKit fails: AVKit overwrote the title at its next update.

As built: the player switches AVKit's publication off and publishes the record itself through MediaPlayer (`RecordingNowPlaying.swift`): title = the lecture (`RecordingsPresentation.title` rules), artist = the course as the sidebar names it (`RecordingsPresentation.courseName`), artwork = the course picture from WeBeep (`core_enrol_get_users_courses` → `overviewfiles`, else `courseimage`; stored as `RemoteCourseSummary.imageURL`, optional in the saved course list), video media type, duration/elapsed/rate, and the remote commands play, pause, toggle, ±10 s skips and scrubbing. MediaPlayer is `dlopen`ed on the first Play like AVKit: +2 images (MediaPlayer, MusicLibrary) on top of the 1151 of a first Play; nothing at launch. If MediaPlayer cannot load, AVKit keeps publishing as before. The window shows the lecture as title and the course as subtitle.

Picture: fetched after playback has started, never awaited; one request at a time, ≤ 10 s, ≤ 2 MB, `image/*` only, HTTPS web-service `pluginfile.php` on WeBeep's host only, redirects refused, token appended only by `WeBeepAPIClient.fetchCourseImage` and never logged; decoded off the main actor to ≤ 512 px (sources over 40 MP refused). Kept in memory for the course on screen only (another lecture of the same course reuses it), released on close; a late picture of a replaced lecture or after close is dropped (`artworkSerial`). Without a picture the record shows the app icon.

Wiring: `RecordingsController.startPlayer` passes `RecordingPlaybackMetadata(recording:course:streamTitle:)` on every play, recoveries included (a recovery reuses the metadata of the lecture already in the player). The course is the one the student chose (the menu line's course, or the page's selected course) when it is the recording's own, else the one WeBeep course with its archive key (`RecordingsController.playbackCourse`); two courses sharing a key thus keep the chosen one's name and picture. The player's `artworkLoader` is `WeBeepAuthenticationController.courseImage`, which reads the token at each fetch and refuses a picture that arrives after an account or site change. The record shows rate 0 while the player buffers; a failed picture is retried by the next play of that course; nothing is fetched when MediaPlayer is missing (AVKit publishes then). Player tests use a silent publisher, so `swift test` never registers remote commands with the system; one test uses the real one.

To verify by hand (cannot be tested in CI): what Control Center's Now Playing, the menu bar Now Playing item and the media keys show and do while a lecture plays, and how the course picture looks.

Privacy and data: the title and the course name are readable by other processes through MediaRemote while the player is open and are cleared on close; the picture address is the only new stored value (an optional field of the saved course list, no token); the picture itself and its bytes never reach disk. ## Zoom (PR #154)

Pinch (1x to 4x), ⌘+ / ⌘= / ⌘− (steps of 0.5 around the centre) and ⌘0 (back to fit); while zoomed, a drag or a scroll pans. `PlayerZoomModel` (pure, covered by `PlayerZoomModelTests`) decides scale, anchor-preserving pinch, pan limits and resizes; `RecordingPlayerWindow` takes the pinch and the pointer events (a pinch begun over the controls is let through) and the three zoom chords, the only ⌘ chords the window takes; `RecordingPlayerController.applyZoom` shows the result through AVKit's public `setMagnification:centeredAtPoint:` plus the clip origin of AVKit's own video scroll view. AVKit's `allowsMagnification` stays off so two handlers never act on one pinch. The zoom is kept across pause and recovery of the same lecture, reset to fit when another lecture is played, never saved. Locating AVKit's video scroll view relies on its view hierarchy (`PlayerVideoViews`), so it is the first thing to recheck on a new macOS; if the views are not found the zoom degrades to AVKit's magnification alone. Whether this holds on macOS releases other than 27 is **unverified**.

## Watch progress (PR #154)

Rules live in Core (`RecordingWatchProgress`, `RecordingWatchSession`, `RecordingWatchEntry`); the user-visible contract is in the sync-behavior specs. How the player's reports feed them:

- **Ticks (memory only).** `onProgress(id, position, duration)` fires from one periodic time observer that exists only while the player is not paused: every 30 s of lecture time (15 s of wall time at 2x), plus AVFoundation's own fires when playback starts, stops or jumps. Nothing is reported before the start is settled (ready and the resume seek landed), so a lecture resumed near its end never reports the 0 shown while the resume is under way. `RecordingsController.playerProgress` observes the fraction in the lecture's in-memory session and publishes it as a *live* value that moves the window's bar and the course's header summary. A tick never writes to disk, never changes the saved summary (the menu) and never moves the next lecture to watch.
- **Checkpoints (disk).** The same four reasons as the resume position: `.paused`, `.closed`, `.replaced`, `.failed` (`RecordingCheckpointReason`). The checkpoint's own position is observed first, because ticks stop at a pause. `RecordingWatchProgress.checkpointCloses` decides what ends the session: `.closed` always; `.replaced` only when a *different* lecture takes the place (a recovery or Play pressed again on the same lecture continues the session, and a replacement with an unknown successor counts as a different lecture); `.paused` and `.failed` never. Only a closing checkpoint can complete a lecture. Quitting reports nothing.
- **Writing.** Events go on a serial chain to the seen history (`RecordingsSeenStore.applyProgress`, `progress` table in `recordings-seen-v2.sqlite`, same owner/course/year/id key). The store decides on a read without a write lock first and returns without opening a transaction when nothing would change; otherwise it decides again inside `BEGIN IMMEDIATE`. A failed checkpoint save is kept (at most 20 sessions) and retried at the next checkpoint; a failed manual tick shows the history banner and the row keeps its saved value. A completion also acknowledges the lecture as seen and clears a saved next lecture that is now done.
- **Fraction.** The player's duration wins; Recman's minutes are the fallback while it is unknown; with neither the position is not observed (an unknown length never reads as 0% or 100%).
- **Un-tick.** Removes the manual tick, keeps the percentage and sets a block on automatic completion; the playing session forgets any crossing it had seen, and a failed checkpoint queued before the un-tick loses its crossing when retried, so an un-tick is never undone by a stale close.
- **Resume point vs progress.** Two separate stores with different rules: the resume point (`recordings-resume.v1`, preserved when Recordings is turned off, forgotten within max(30 s, 2%) of the end) and the progress (removed with the namespace on turn-off, 90% on close). Do not merge them: they answer different questions (where to restart vs. how much of the course is done).

## Plays survive closing Settings (PR #154)

Before: closing the Settings window or the Recordings page cancelled a Play that was queued, for example behind a recovery. Now `RecordingsController.suspend` keeps any queued or running Play (from the window or the menu bar line) and any recovery, and a sync refresh still waiting; it drops only the listings the page alone wanted and the other clicks (Open in browser, Copy link), and closes the Recman browser when the queue has drained (`closesBrowserWhenIdle`). Consequence to know about: the Webex sign-in window or the browser fallback can appear a few seconds after Settings was closed. A change of identity (turn-off, logout, account or site change) still cancels everything. The sync-behavior specs were updated accordingly.

## Menu bar Play (PR #154)

A click on a course's line in the status menu reaches `WeBeepAuthenticationController.playNextRecording` through the `nonisolated` action and the `Task { @MainActor }` hop required by AGENTS.md (#30/#31). The click carries only the account, the course and the archive key (`RecordingMenuTarget`); the lecture is re-resolved on the main actor from the saved summary and re-validated (`validatedNext`: same course code and year, a Recman preview link for its own id), because the menu can be older than the data. A stale click does nothing and never creates the Recordings controller. An accepted click uses the Play button's path (`RecordingsController.playFromMenu`): stream lookup, resume position, seen, progress, recovery and fallbacks are the same. If the controller cannot play without the window (Recordings off for it, Polimi sign-in needed or running, an invalid stored lecture) or the Play fails (no email in use, lecture not available), BeepBar opens on that course's Recordings page (`onMenuPlayNeedsPage`), where the usual message or "Accedi con Polimi" shows.

## Refreshing listings at every sync never plays (PR #154)

`RecordingsController.refreshForSync`, called by the sync's follow-up after Core's `RecordingsSyncPolicy` decided, queues only `.list` jobs through the same worker and `record` as the page: **it never calls `stream(for:)`**, never opens a player, a browser window or a sign-in window, and never downloads video (offline download stays out, #87). A lapsed Polimi session ends it as `.needsSignIn` without a window; with no saved session the browser is not even created. Its courses go after what the page queued and never replace it; the browser closes when the queue has drained if no page is on screen. The follow-up lives outside the sync task, so the quit path is unchanged. Cost measurement of this refresh against the live service is **not done**: see the performance plan and `recordings-validation.md`.

## Compact controls

The inline controls style (measurements in "Player findings" above) is applied by `AVKitLoader.controlsConfiguration`, with frame stepping, sharing, full-screen and timecode buttons off. In full screen AVKit always uses its floating panel.
